# Rhythm

모바일 웹 리듬 게임 (Vite + TypeScript, Canvas 2D, Web Audio). 진행 상황: **STEP 5 완료** (Firebase 온라인 저장). 모든 STEP 구현 완료.

## 실행

```bash
npm install
npm run dev          # http://localhost:5173  (같은 와이파이의 폰에서는 터미널에 뜨는 Network 주소)
npm run build        # 타입체크 + 프로덕션 빌드
npm run preview      # 빌드 결과 확인
npm test             # 단위 테스트 (vitest): 분석 알고리즘·설정·곡 목록·맵 코덱·outbox
npm run test:rules   # Firestore 보안 규칙 테스트 (에뮬레이터 자동 실행, Java 필요)
npm run emulators    # 로컬 Auth+Firestore 에뮬레이터  →  npm run dev:emu 로 앱 연결
```

## STEP 5 온라인 기능 (Firebase)
설정 방법은 **[docs/FIREBASE.md](docs/FIREBASE.md)**. Firebase 를 설정하지 않으면 온라인 버튼만 숨겨지고 게임은 그대로 동작합니다.

- **로그인**: 앱을 열면 익명 로그인 → 설정에서 **Google 계정 연결**(익명 계정의 uid·기록이 유지됨, 이미 다른 계정에 연결된 구글 계정이면 그 계정으로 전환)
- **Firestore**: `users/{uid}`(닉네임·설정), `maps/{곡지문}_{난이도}`(맵 JSON + 만든 사람 uid), `scores/{id}`(점수·정확도·콤보·시간). 오디오 원본은 저장하지 않음
- **곡 지문 흐름**: 같은 곡을 올리면 ① 로컬 캐시 → ② 온라인에 저장된 맵 → ③ 없을 때만 분석 후 저장
- **맵 공유**: 준비 화면 **🔗 맵 공유**(링크 복사/공유 시트) → 받은 사람은 링크를 열거나 메뉴 **공유 맵 불러오기**에 링크·ID 붙여넣기 → 각자 자기 곡 파일 선택 (곡 지문이 다르면 확인 후 진행)
- **리더보드**: 곡·난이도별 상위 20명 (준비/결과 화면의 🏆). 개인 최고 기록을 갱신했을 때만 업로드
- **오프라인**: 서비스 워커가 앱을 캐시해 비행기 모드에서도 열리고 플레이 가능. 점수·맵은 기기에 보관했다가 온라인 복귀 시 자동 동기화 (메뉴에 `업로드 대기 N` 표시)
- **보안 규칙** (`firestore.rules`): 인증된 사용자만, 본인 문서만 쓰기, `scores` 생성만 허용(수정·삭제 불가), 맵은 생성만·노트 2500개 제한, 점수 범위·서버 시각 검증

### STEP 5 테스트 체크리스트
**Firebase 없이 (설정 전)**
- 메뉴에 온라인 버튼이 없고, 설정 화면의 온라인 계정 영역에 설정 안내가 보임 / 게임은 정상
- 배포 주소에서 한 번 열어 본 뒤 **비행기 모드로 새로고침** → 앱이 열리고 곡 업로드·플레이가 됨 (홈 화면에 추가한 앱도 동일)

**Firebase 설정 후**
- 메뉴 상단에 `☁ Player1234 (익명)` 표시
- 곡 업로드 → 플레이 → 결과 화면 `최고 기록은 리더보드에 자동으로 올라가요` → **🏆 리더보드**에 내 닉네임이 강조되어 표시
- 설정 → 닉네임 변경 → 리더보드 이름에 반영 (새 점수부터)
- **Google 계정 연결** → 이메일이 표시되고 기록이 유지. 다른 기기에서 같은 구글 계정으로 연결하면 닉네임·설정이 따라옴
- **비행기 모드로 플레이** → 결과 후 메뉴에 `업로드 대기 1` → 비행기 모드 해제 → 잠시 후 대기가 사라지고 리더보드에 반영
- **친구 폰**: 🔗 맵 공유 링크를 보내 → 친구가 링크를 열면 곡 파일 선택 화면 → 같은 곡 파일을 고르면 분석 없이 바로 시작, 리더보드에 서로의 기록이 보임
- 구글 로그인에서 오류가 나면 앱이 보여 주는 안내(승인된 도메인, 로그인 방법 활성화 등)를 따를 것

## STEP 4 테스트 체크리스트
- 메뉴 → **⚙ 설정**: 노트 속도(1~10), 판정 오프셋(±300ms, −10/−1/+1/+10 버튼, 길게 누르면 반복), 음악/효과음 볼륨. 값은 **새로고침/재접속 후에도 유지**(localStorage)
- **메트로놈으로 오프셋 자동 보정**: 게임에서 쓸 기기·이어폰 그대로 → 시작 → 준비 4박 후 메트로놈 소리에 맞춰 큰 원을 16번 탭 → 측정값(예: +88ms)과 편차 확인 → **적용**. 블루투스 이어폰이면 눈에 띄게 큰 +값이 나와야 정상
- 보정 후 플레이: 노트가 소리와 맞게 느껴지는지, 안 맞으면 설정에서 ±1/±10으로 미세 조정
- **결과 화면**: 랭크·점수·판정 수·최대 콤보·정확도, 최고 기록 갱신 시 `NEW BEST`. 평균 타이밍이 한쪽으로 8ms 이상 치우쳤으면 "오프셋 N → M ms 적용" 버튼이 뜸 (다음 플레이부터 적용)
- **다시 하기**: 같은 곡·난이도로 즉시 재시작
- **최근 플레이한 곡**: 곡별 BPM·길이·플레이 횟수와 난이도별 최고 기록(랭크/점수). 목록은 터치로 스크롤, ✕로 삭제(최대 12곡)
- 곡 항목을 누르고 **같은 파일을 다시 선택**하면 분석 없이 바로 준비 화면(맵은 곡 지문으로 로컬 캐시, 오디오는 저장하지 않음). 마지막에 고른 난이도도 기억
- 시크릿 모드 등 저장소를 못 쓰는 환경에서도 앱이 죽지 않고 동작해야 함(설정/기록만 유지 안 됨)

### 오프셋의 의미
`판정 오프셋(+)` = 소리가 늦게 들리는 만큼 노트와 판정을 **늦게** 처리. 보정 화면은 메트로놈 박 시각과 탭 시각(`event.timeStamp` → 오디오 시계)의 차이를 절사평균으로 구하므로 출력 지연과 개인 탭 습관이 함께 반영됩니다.

## STEP 3 테스트 체크리스트
- 파일 선택 → **분석 진행률**(0→100%) → 준비 화면에 **BPM**과 난이도(쉬움/보통/어려움)별 노트 수·밀도(노트/초) 표시
- 분석 중에도 화면이 멈추지 않고(워커), **취소**로 메뉴에 돌아갈 수 있는지
- 난이도를 바꿔도 재분석 없이 즉시 전환되는지 (3개 난이도를 한 번에 생성)
- 플레이하면서 확인: 노트가 **곡의 박자(킥·스네어)와 맞는지**, 킥 같은 저음은 **바깥 레인**, 하이햇·멜로디 같은 고음은 **안쪽 레인**에 오는지, 지속되는 소리가 **롱노트**가 되는지
- 쉬움 ≈ 2노트/초, 보통 ≈ 3~5, 어려움 ≈ 5~8 정도가 목표. 너무 많거나 적으면 아래 *튜닝* 참고
- 같은 곡을 다시 올리면 항상 같은 맵이 나오는지 (결정적)
- `npm test` 가 통과하는지

### 자동 맵 생성 (`src/analysis/`)
```
PCM(모노, 2배 디시메이션) → FFT 1024 / hop 256 → 3개 대역(저 30–250Hz · 중 250–2k · 고 2k–10k)별 spectral flux
  → 대역 가중합 onset 함수 → 적응형 임계값(±0.4초 이동평균 × alpha + delta) + 지역 최대값 = onset 후보
  → BPM/박자 위상: 자기상관(+옥타브 보정) → 콤(comb) 필터로 0.05 BPM 단위 정밀화
  → 박자 격자 스냅 (onset 들이 격자에 실제로 붙을 때만, 최대 45ms 이동)
  → 강한 onset 순으로 선택 (최소 간격 · 1초당 최대 이벤트 수)
  → 지속음 검출 → 롱노트 → 레인 배정 (저음=바깥, 고음=안쪽, 중음=덜 쓴 레인) · 동시 입력 제한
```
- 워커(`worker.ts`)에서 실행하고 진행률을 보고. 3개 난이도 맵을 한 번에 만든다.
- 맵 JSON: `{ songHash, title, bpm, offset, difficulty, notes: [{t, lane, dur}] }` (`offset`=첫 박 시각, 박자선 표시용 선택 필드)
- 박자가 불확실한 곡(무박/라이브 연주 등)은 스냅하지 않고 onset 원래 시각을 쓴다.
- **튜닝**: 난이도별 임계값·최소 간격·밀도·동시 입력 수·롱노트 기준은 `src/analysis/difficulty.ts`, 대역 경계·가중치는 `spectral.ts`.

## STEP 1 테스트 체크리스트

### 타이밍 설계
모든 시간은 `AudioContext.currentTime` 기준입니다. 렌더 프레임(rAF)이 아니라 `audio/clock.ts`가
오디오 시계에 고정된 시각을 제공하고, 터치 이벤트는 `event.timeStamp`(실제 입력 시각)를 같은
시간축으로 변환해 판정하므로 프레임 간격(16ms)의 영향을 받지 않습니다.
출력 지연(블루투스 이어폰 등)은 설정의 판정 오프셋(`Game.offset`)으로 보정합니다 (설정 화면에서 수동 조정 또는 메트로놈 자동 보정).

### 판정 / 점수
- 윈도우: Perfect ±50ms, Great ±100ms, Good ±150ms, 그 밖은 Miss
- 정확도 가중치: Perfect 100%, Great 75%, Good 40%, Miss 0%
- 점수 = 정확도 90만 + 최대콤보 비율 10만 (만점 1,000,000)
- 랭크: S ≥ 95%, A ≥ 85%, B ≥ 70%, 그 외 C
