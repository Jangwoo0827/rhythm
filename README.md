# Rhythm

모바일 웹 리듬 게임 (Vite + TypeScript, Canvas 2D, Web Audio). 진행 상황: **STEP 3 완료** (자동 맵 생성). 다음: STEP 4 오프셋 보정·설정·곡 목록.

## 실행

```bash
npm install
npm run dev          # http://localhost:5173  (같은 와이파이의 폰에서는 터미널에 뜨는 Network 주소)
npm run build        # 타입체크 + 프로덕션 빌드
npm run preview      # 빌드 결과 확인
npm test             # 분석 알고리즘 단위 테스트 (vitest)
```

### 폰에서 테스트 (같은 와이파이)
1. PC에서 `npm run dev` 실행 → 터미널의 `Network: http://192.168.x.x:5173/` 확인
2. 폰 브라우저(크롬/사파리)에서 그 주소로 접속 (PC 방화벽이 5173 포트를 막고 있으면 허용)
3. 접속이 안 되면 같은 와이파이인지, 게스트 와이파이(기기 간 격리)가 아닌지 확인
4. 홈 화면 추가(PWA)·서비스워커·구글 로그인은 HTTPS가 필요하므로 STEP 5에서 별도 안내 (STEP 1~4는 http로 충분)

### PC에서 테스트
`D F J K` 키가 레인 1~4. 크롬 개발자도구의 모바일 에뮬레이션(터치)으로도 가능.

## STEP 3 테스트 체크리스트
- 파일 선택 → **분석 진행률**(0→100%) → 준비 화면에 **BPM**과 난이도(쉬움/보통/어려움)별 노트 수·밀도(노트/초) 표시
- 분석 중에도 화면이 멈추지 않고(워커), **취소**로 메뉴에 돌아갈 수 있는지
- 난이도를 바꿔도 재분석 없이 즉시 전환되는지 (3개 난이도를 한 번에 생성)
- 플레이하면서 확인: 노트가 **곡의 박자(킥·스네어)와 맞는지**, 킥 같은 저음은 **바깥 레인**, 하이햇·멜로디 같은 고음은 **안쪽 레인**에 오는지, 지속되는 소리가 **롱노트**가 되는지
- 쉬움 ≈ 2노트/초, 보통 ≈ 3~5, 어려움 ≈ 5~8 정도가 목표. 너무 많거나 적으면 아래 *튜닝* 참고
- 같은 곡을 다시 올리면 항상 같은 맵이 나오는지 (결정적)
- `npm test` 가 통과하는지

### 자동 맵 생성 (`src/analysis/`)
```
PCM(모노, 2배 디시메이션) → FFT 1024 / hop 256 → 3개 대역(저 30–250Hz · 중 250–2k · 고 2k–10k)별 spectral flux
  → 대역 가중합 onset 함수 → 적응형 임계값(±0.4초 이동평균 × alpha + delta) + 지역 최대값 = onset 후보
  → BPM/박자 위상: 자기상관(+옥타브 보정) → 콤(comb) 필터로 0.05 BPM 단위 정밀화
  → 박자 격자 스냅 (onset 들이 격자에 실제로 붙을 때만, 최대 45ms 이동)
  → 강한 onset 순으로 선택 (최소 간격 · 1초당 최대 이벤트 수)
  → 지속음 검출 → 롱노트 → 레인 배정 (저음=바깥, 고음=안쪽, 중음=덜 쓴 레인) · 동시 입력 제한
```
- 워커(`worker.ts`)에서 실행하고 진행률을 보고. 3개 난이도 맵을 한 번에 만든다.
- 맵 JSON: `{ songHash, title, bpm, offset, difficulty, notes: [{t, lane, dur}] }` (`offset`=첫 박 시각, 박자선 표시용 선택 필드)
- 박자가 불확실한 곡(무박/라이브 연주 등)은 스냅하지 않고 onset 원래 시각을 쓴다.
- **튜닝**: 난이도별 임계값·최소 간격·밀도·동시 입력 수·롱노트 기준은 `src/analysis/difficulty.ts`, 대역 경계·가중치는 `spectral.ts`.

## STEP 2 테스트 체크리스트
- 메뉴 → **음악 파일 선택** → mp3 / m4a / wav / ogg 선택 → 준비 화면(제목, 길이, 노트 수) → **START**
- 곡이 재생되고 노트가 곡 시작(3초)부터 내려오는지. 소리/노트 싱크는 STEP 1과 같은 방식으로 판정 (어긋나면 STEP 4 오프셋 화면에서 보정)
- **상단 가운데 ❚❚ 버튼**(또는 PC에서 Esc) → PAUSED → 계속하기(3-2-1 후 재개) / 처음부터 / 나가기
- 앱 전환·화면 잠금 시 자동 일시정지
- 깨진 파일 / 5초 미만 / 12분 초과 파일은 안내 메시지 후 메뉴로 복귀
- 곡이 끝나면 결과 화면 → 다시 하기(같은 곡) / 처음으로

## STEP 1 테스트 체크리스트
- START → 3·2·1 카운트다운 후 노트 낙하, 백킹 사운드가 노트와 맞는지
- 탭 노트: 판정선에 맞춰 탭 → PERFECT / GREAT / GOOD, 빠르면 FAST, 늦으면 SLOW 표시
- 안 치면 MISS, 콤보 끊김
- 롱노트: 누르고 있다가 끝에서 떼기. 도중에 떼면 MISS + 콤보 끊김
- 멀티터치: 롱노트를 누른 채 다른 손가락으로 다른 레인 탭 (8마디), 동시치기 (9마디)
- 화면을 스크롤/핀치/길게 눌러도 아무 일도 일어나지 않는지
- 곡이 끝나면 결과 화면(점수·정확도·랭크) → 다시 하기
- 홈 버튼/앱 전환 시 자동 일시정지

## 구조
```
src/
  audio/     Web Audio 엔진, AudioContext 기반 Clock, 파일 디코드(loader), 곡 지문(songHash), 테스트 사운드 합성
  game/      게임 로직(game, judge, score), 샘플 맵, 입력, 렌더러, 이펙트, 원근 레이아웃
  ui/        DOM 오버레이(시작/일시정지/결과), 브라우저 제스처 차단
  analysis/  FFT·spectral flux·onset 검출·BPM 추정·난이도별 맵 생성 (Web Worker)
  firebase/  (STEP 5) Auth / Firestore
```

### 타이밍 설계
모든 시간은 `AudioContext.currentTime` 기준입니다. 렌더 프레임(rAF)이 아니라 `audio/clock.ts`가
오디오 시계에 고정된 시각을 제공하고, 터치 이벤트는 `event.timeStamp`(실제 입력 시각)를 같은
시간축으로 변환해 판정하므로 프레임 간격(16ms)의 영향을 받지 않습니다.
출력 지연(블루투스 이어폰 등)은 `Game.offset`으로 보정하며 보정 화면은 STEP 4에서 추가됩니다.

### 판정 / 점수
- 윈도우: Perfect ±50ms, Great ±100ms, Good ±150ms, 그 밖은 Miss
- 정확도 가중치: Perfect 100%, Great 75%, Good 40%, Miss 0%
- 점수 = 정확도 90만 + 최대콤보 비율 10만 (만점 1,000,000)
- 랭크: S ≥ 95%, A ≥ 85%, B ≥ 70%, 그 외 C
